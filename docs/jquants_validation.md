# J-Quants APIによる財務指標の数値検証（2026-10-07〜）

## 背景・全体設計

当DWHが独自ロジックで算出した財務指標（`mart__jpx_edinet__quarterly_fundamentals`）を、
第三者データ（J-Quants API）と突き合わせて検証するプロジェクト。IR Bank（利用規約で
商用・体系的ダウンロードを禁止）は候補から除外し、J-Quants（Freeプラン、月額0円・
5リクエスト/分・直近12週を除く過去2年分）を採用した。

- レイク層（`edinet-dl/services/jquants-validate/`）: `GET /v2/fins/summary`を日付単位で
  全量取得し、生レスポンスをそのまま保存（解釈しない）。認証は`x-api-key`ヘッダーの
  静的APIキー。
- ウェアハウス層: `cleansed__jquants__fin_summary`（型付けのみ、DuckDBの`read_json_auto`
  でレイクの生JSONを直接読む。他のcleansedモデルと異なりlanding層を経由しない）。
  `tags=['jquants_validation']`を付け、日次ビルド（`dbt build --exclude
  tag:jquants_validation`）から常に除外する（検証時のみ`--select tag:jquants_validation`
  で手動実行）。
- 照合スクリプト: `transform/validate/compare_jquants.py`（不定期手動実行、
  `cleansed__jquants__fin_summary`と`mart__jpx_edinet__quarterly_fundamentals`の
  2つのParquetを読み企業×期間ごとに突き合わせる）。

J-QuantsのCodeは5桁（末尾1桁は株式種別）、DWHのjpx_codeは4桁のため`left(code,4)`で
結合する。REIT（投資法人）はEDINETの書類一覧APIがsecCodeを付与しないためedinet-dlが
そもそも取得しておらず、対象外として件数のみ報告する（別タスク化、詳細は
`edinet-dl/services/edinet-dl/CLAUDE.md`「REIT（投資法人）対応の検討」参照）。

## 全量照合の結果推移

523営業日分（2024-07-15〜2026-07-15）を全量取得して照合。

| 時点 | sales | eps | bps | dividend_per_share | shares_outstanding |
|---|---|---|---|---|---|
| 初回全量照合 | 262 | 334 | 308 | 19 | 399 |
| 2026-10-10時点 | 203 | 133 | 89 | 15 | 51 |

比較件数（分母）は各約15,000〜16,000件（REIT 237件は対象外、件数のみ）。

## 解消した課題（PR #43〜#51、本番デプロイ済み）

### 課題1: 株式分割タイミングの構造的差異（PR #43）

決算期末が株式分割・併合の**権利確定日(ex_rights_date)〜効力発生日(effective_date)**の
間に位置する開示では、DWHは分割前の株数を保持する一方、J-Quantsは分割後の株数を遡及
表示する（ニデック(6594)の実機ケースで発覚）。`mart__jpx_edinet__disclosed_fundamentals`
が既に持つ調整係数で許容:
- `shares_outstanding`: `shares_period_end_cum_adj`（効力発生日基準）で除した値が
  一致すれば一致とみなす。399件中339件がこのパターンで解消。
- `eps`/`bps`/`dividend_per_share`: 同じ構造的差異があるため`period_end_cum_adj`
  （権利確定日基準、EPS/BPS/配当用に別途存在する係数）を同様に適用（PR #49）。
  開示値自体の円単位丸めが除算で拡大されるため、許容誤差を係数の逆数に比例させる
  （`0.01 / adj`）。

残り（係数がNULL・1.0でも不一致、複数回の分割が重なり単一係数では補正できない等、
約18件）は未解明の残差として受容している（`8421`・`9249`等）。

### 課題2: J-Quants側の重複開示行（PR #46）

同一(jpx_code, period_end)にJ-Quants側が複数行を持つことがある（全31,289組中1,146組。
779組は同じ値の重複掲載、367組は決算短信の訂正等で値が実際に変化）。disc_date・
disc_timeが最新の1行を残す（DWH側の`is_preferred_actuals`と同じ「最新開示優先」の
考え方）。

この規則でも一致しないケースがある（143A・工藤建設(1764)等で確認: 「最新を残す」が
必ずしもEDINET確定値と一致する側を選ぶとは限らない）。どちらを残しても一方で新たな
不一致が生じることを実機確認済みのため、ルールの欠陥ではなく本物の差異として受容する。

残っている579件のうち、重複起源の不一致は105件（18%）のみで、**残り82%は重複と
無関係**（別の原因）と判明している。

### sales_matchesのバグ（PR #47）

完全一致する値でも、その値自体が100万円単位の倍数でなければ、切り捨て後の値
（`dwh_v // 1_000_000 * 1_000_000`）と比較して誤って不一致と判定していた。まず完全
一致を試すよう修正（`shares_matches`と同じパターン）。9件解消。

### 根本バグ: EDINET訂正報告書が一切取り込まれていなかった（PR #44・#45）

**発見の経緯**: イシン(143A)の実機データで、訂正有価証券報告書(2025-11-14提出)に
EPS訂正後の値がテキストブロックに記載されているのに、DWH側が訂正前の値
(92.89)を使い続けていることを発見。

**根本原因1**: `cleansed__edinet__report_periods.sql`が`doc_type_code in
('120','140','160')`（有報・四半期報告書・半期報告書の**オリジナルのみ**）を対象に
しており、訂正系（130=訂正有報、150=訂正四半期、170=訂正半期）が最初から除外されて
いた。レイク層（edinet-dl）には訂正書類は既に正しく取得済みだったため、欠落はウェア
ハウス層のみ。訂正書類はEDINET側が`periodStart`/`periodEnd`を常にNULLで返すため、
`parentDocID`で訂正元書類から補完する必要がある（訂正元が edinet-dl のバックフィル
開始(2016-08-13)より前で取得範囲外の場合は解決不能、1,431件除外）。（PR #44）

**根本原因2**: PR #44適用後も、`intermediate__edinet__{jgaap,ifrs,usgaap}_
financial_facts`の文脈ID判定（`doc_type_code`で分岐、`'120'/'140'/'160'`のみ対応・
`else false`）が訂正系docTypeCodeに対応しておらず、訂正書類からは一切ファクトが
抽出されていなかった。サンテック(1960)の実機データで、訂正有報に構造化タグとして
正しいEPS(-48.58、J-Quantsと完全一致)が存在するのに抽出できていないことを確認。
`130`→`120`、`150`→`140`、`170`→`160`と同じcontext_id規則を適用（実機で150/170の
サンプル書類からも同じ規則であることを確認）。（PR #45）

**列単位の値救済ロジック**: 訂正書類のXBRLは訂正した項目だけを再タグ付けする実務が
あるため、`mart__edinet__financial_indicators`を行単位（最新1件を選ぶ）から列単位
（各指標ごとに「新しい書類から見て最初に見つかった非NULL値」を採用）の結合方式に
変更。出典混在（ある列は新しい書類、別の列は古い書類という不整合な組み合わせ）の
リスクを検証: 複数書類が存在する4,829グループ中、単一書類では説明できない「混在」は
1件のみで、安全と判断した。（PR #45）

### 課題3: DWH側の異常値（PR #50・#51）

養命酒製造(2540)・イーストアー(4304)・カオナビ(4435)のEDINET提出XBRL自体（経営指標等
タグ、連結・個別どちらも）に、本来数十〜数千円台であるべき値ではなく数千万〜数百億円
台の値が直接記載されていることを実機確認。**DWHの抽出ロジックの問題ではなく、提出者
側のデータ不備**と判断（同一書類内で当期・前期列だけが異常、前々期以前は正常）。

Human-in-the-loopの方針に基づき、`severity=warn`の妥当性チェックを追加
（`assert_mart__edinet__financial_indicators_eps_bps_plausible`、閾値100万円）。
閾値の根拠: 正当な極端値の最大（信金中央金庫のBPS約32万円＝特殊な資本構成、
LITALICOの発行済株式数200株という特殊な期のEPS/BPS約86万円＝net_assets/sharesで
内部的に整合）は約86万円にとどまる一方、異常な値は最小でも約2,080万円から始まり、
24倍以上のギャップがある。全量データで検査した結果、当初の3件に加え新たに3件
（計6書類）を検出した。（PR #50）

**Slack通知のメタ駆動設計**（PR #51）: どのdbtテストをSlack通知対象にするかを、
テスト本体から切り離した別の管理リストではなく、**テスト自身の`config()`に
`meta={'notify_slack': true}`を付けるだけ**で済むようにした。日次ビルドの
`tag:jquants_validation`除外（deny-list方式）と同じ考え方で、「通知すべきか」の
判断を対象と同じ場所に置くことで、将来テスト追加時の記入漏れを構造的に防ぐ。

実装（`transform/flows/test_violations.py`）: `dbt build`後の`target/manifest.json`
（各テストのmeta）と`target/run_results.json`（今回の実行結果。dbt 1.8+では
`compiled_code`に解決済みSQLそのものを含む）を突き合わせ、`notify_slack=true`かつ
今回warnが出たテストだけ、その`compiled_code`を再実行して該当行を取得する
（SQLロジックを二重管理しない）。`daily_transform.py`に新タスクとして追加し、通常の
ビルドサマリ通知とは別にSlackへ投げる。

## 残っている不一致の原因調査

### 複数回の決算訂正を持つ企業（未解決、本物の差異と判断）

トーシンホールディングス(9444)で、同一期間に対し**3回の独立した訂正**（2025-02-14・
2025-10-31・2025-11-18）が行われ、それぞれ異なる値（売上高・EPSとも大きく変動、
黒字から赤字への転落を含む）を持つことを確認。J-Quantsのスナップショット
（disc_date=2025-02-14）は1回目の訂正と一致するが、DWHは（正しく）最新の値を
採用しており、参照している「訂正の版」が異なるため不一致になる。

複数期間にわたって不一致を持つ14社を全量データで確認したところ、**11社が全期間の
70〜95%という極めて高い割合でEDINET訂正履歴を持つ**ことを確認した（9444と同じ
パターンが広く一般化することを裏付け）。

| 企業 | 訂正ありの期間 / 全期間 |
|---|---|
| Abalance(3856) | 18/19 |
| トーシンHD(9444) | 18/20 |
| 河西工業(7256) | 17/18 |
| ピクセルカンパニーズ(2743) | 14/17 |
| BlueMeme(4069) | 16/17 |
| アドバンスクリエイト(8798) | 15/19 |
| ジェイ・イー・ティ(6228) | 7/8 |
| ナブテスコ(6268) | 10/19 |
| ハマイ(6497) | 10/19 |
| イリソ電子工業(6908) | 10/18 |
| エア・ウォーター(4088) | 11/18 |

これは一部の期間だけの訂正ではなく、**過去の全期間を一括で大規模に遡及訂正した**
という、会計上の問題（不正・誤謬の発覚による包括的な再訂正）を抱えた企業群の典型的
な特徴と考えられる。残り3社（三井住友トラストHD(8309)・信金中央金庫(8421)・
進学会HD(9760)）は訂正が1件のみで、同じパターンには当てはまらない（未調査）。

### J-Quantsが一部のEDINET訂正を反映しない理由（実機確認済み）

トーシンHD(9444)の2025-10-31・2025-11-18提出の訂正について、J-Quants側の該当日の
生データを直接確認した。**両日のファイルは正しく取得済みで、同社の別期間（直近の
通常開示）のデータは実際に含まれている**ため、Freeプランの12週遅延（取得window自体）
が原因ではない。しかし、問題の訂正対象期間（2023年4月期〜2024年1月期）については、
J-Quantsのデータ自体に2025-02-14時点（1回目の訂正）の記録しか存在せず、2回目・
3回目の訂正は一切反映されていない。

**推測される理由**: J-Quantsの`/fins/summary`は日付ごとに「その日に発生した開示
イベント」を返す設計で、実体はTDnet（決算短信等の適時開示）のannouncementに紐づいて
いると考えられる。EDINETの訂正有価証券報告書が、TDnet側の新規announcementを伴わずに
提出された場合（過去複数期をまとめて遡及訂正するケースに多い）、J-Quantsの日付ベース
フィードには一切現れないと考えられる。これはFreeプランの契約上の制約ではなく、
J-Quants自体のデータソース（TDnetに現れないEDINET単独の訂正は原理的に追えない）に
起因するため、Lightプランへの契約変更でも解消しない可能性が高い。

## 未解決・今後の検討候補

- 課題1残差（約18件）: 複数回の分割が重なり単一の係数では補正できないケース
  （`8421`・`9249`等）。EDINETの分割イベント自体（権利確定日・効力発生日）を直接
  参照して単発の分割比率を計算すれば原理的に解消できるが、既存の累積係数を使う
  簡易な方法では対応できない。
- 課題2残差（重複があった期間の18%）: 最新優先でも説明できない、J-Quants側の決算
  短信訂正とEDINET確定値が実際にズレている本物の差異。
- 三井住友トラストHD(8309)・信金中央金庫(8421)・進学会HD(9760): 複数回訂正パターンに
  当てはまらない残り3社、未調査。
- REIT（投資法人）対応: `edinet-dl/services/edinet-dl/CLAUDE.md`参照、別タスク化済み。
